## 它做什么

`to-questionnaire` 把一个你自己定不下来的决定变成一份**问卷**：一个 Markdown 文档，你把它交给那个恰好握着你缺的东西的人，让异步填，或者你俩在一次会议上过一遍。

它追问的是这次**发送**，从来不是那个主题。就话题本身做一轮访谈毫无意义，因为你正是因为不懂这个话题才去写信给别人。所以它只问两件你总能答上来的事（这封信发给谁，以及你需要从他那里拿回什么），并让文档里的每一个问题都对准这两者之间的那个**缺口**。

## 什么时候找它

要输入 `/to-questionnaire` 才能调用它，[agent](https://www.aihero.dev/ai-coding-dictionary/agent)（代理）不会自己去找它。

当一个决定卡在只存在于另一个人脑子里的知识上时用它：一个客户、一位领域专家、一个掌握业务规则的高管、一个和你不同办公室的同事。你要哪份 Skill，取决于答案在哪里：

| 答案在……里 | 该找谁 |
| --- | --- |
| 你自己的脑子里，只是还没磨利 | [grill-me](https://aihero.dev/skills-grill-me) |
| 代码库里 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 别人的脑子里 | `to-questionnaire` |
| 目前谁脑子里都没有，这个问题需要一个可以反应的东西 | [prototype](https://aihero.dev/skills-prototype) |

常见的场景是一场 [grilling](https://www.aihero.dev/ai-coding-dictionary/grilling)（追问）session（会话）卡住了，因为它引出的有些问题不归你回答。在同一个对话里运行 `/to-questionnaire`，把那些问题带到线下，然后把答案带回来，接着往下走。

## 是发送，不是主题

这场访谈是两个来回，然后它就停。

- **发给谁？** 他的角色、他的专长、他与你的关系。这决定基调，也决定文档要携带多少上下文。一个外部客户需要先被交代背景；一个队友不需要。
- **你需要拿回什么？** 那些你一个人定不下来的具体决定或事实。这会变成成稿的核对清单。你点出的每一项，都会有一个问题对准它。

此后的一切都只是起草。这份 Skill 把文件写到当前目录下，命名成 `to-questionnaire-<slug>.md`。没有安装，没有工作区，也没有任何东西要配置。

## 这份文档

这份文档是一份**探需问卷**，因为你缺上下文，而收件人有。这决定了它的形状：

- 一行目的，点明依赖它的那个决定，外加一小节上下文，给那些完全不了解你背景的收件人。
- 问题按**最重要的排在最前**的顺序排列，并分在若干主题标题下，因为异步意味着你可能只争取到一次填写。
- 一个问题只有一个想法，绝不复合，下面留一个作答的起头；只在一个问题可能被误读的时候，才加一行"为什么这件事重要"。
- 明确允许回答"我不知道"，因为一个被标出来的不确定是有用的，而一个读起来像事实的自信猜测不是。
- 一个收尾的兜底问题：还有什么我们没问到、而我们应该知道的？

这份文档刻意不是两样东西。它不是**分叉式**的。问题是一张扁平的、分了组的清单，不是一棵你答了 A 就跳过 D 节的树。它也**不支持多收件人**。一次运行只为一个人产出一份文档。

## 常见问题

**它会读我的追问 session，并从里面提取问题吗？**
不会作为一个独立步骤。这份 Skill 没有摄入阶段。它先问发送这件事，然后起草。让它在一次追问 session 之后仍然好用的原因是，你在**同一个对话**里运行它，所以那场 [session](https://www.aihero.dev/ai-coding-dictionary/session) 已经在 [context](https://www.aihero.dev/ai-coding-dictionary/context)（上下文）里，起草时可以直接取用。如果你在一场新 session 里启动它，它对之前的追问一无所知，而你在回答"你需要拿回什么？"的时候就得自己把主题重新交代一遍。

**缺的那些答案不在同一个人那里。它能按收件人拆开吗？**
不能。第一步要的是*那个*收件人，单数，这份 Skill 会把整份文档的基调和上下文对准他。如果三个人各握着答案的三部分，就跑三次，一人一次。有人要过一份文档按学科或角色把问题路由出去，但那个没做出来。

**问题之间是有依赖的吗？它会根据前面的答案跳过某些小节吗？**
不会。依赖式问题那个设计探讨过，但没有发布。输出是一份静态文档：分组按主题、最重要的排在最前、每个问题都活着。对它的反对意见是公允的。一个 [model](https://www.aihero.dev/ai-coding-dictionary/model)（模型）在真实回答之前就规划两三个以上的问题，规划得很差，而一份分叉式文档必须在每一个答案之前就把所有问题规划完。

**如果收件人也不知道呢？**
文档会告诉他可以说不知道。它明确地请求"我不知道"和部分回答。一个被标出来的不确定比一个猜测值钱，因为一个含糊的回答和一个自信的错误回答，回到你的上下文里之后长得一模一样。

**它会把它发到什么地方吗（Slack、工单系统、邮件）？**
不会。它在当前目录写一个 Markdown 文件，并把路径告诉你。投递是你的事：把它粘进一个 [工单](https://www.aihero.dev/ai-coding-dictionary/ticket)，丢进一条 Slack 线程，附在一封邮件上，或者在共享屏幕上打开它当场过一遍。这四种人们都手动做过。

**这不就是批量模式的 `/grill-me` 吗？**
不是。`grill-me` 本来就按**轮次**提问。它一次问出所有开放问题的完整 frontier（前沿），然后根据你的回答重新计算，所以它已经满足了"把所有问题一次给我"这个需求。`to-questionnaire` 的区别在另一个轴上。它关心的是答案在谁的脑子里，不是问题怎么送出去。要你自己更快回答它们，用 `grill-me`。要把它们从别人那里取出来，用这份。

**没有 Skill 我直接问 agent 不也行吗？**
行，而且在它存在之前很多人就是这么干的：`OPEN_QUESTIONS.md` 文件、发给客户的电子表格、每个未答问题建一张"需要更多信息"的工单。这份 Skill 给你两样东西：访谈不会漂到主题上去，而且文档出来是一种非技术收件人也填得动的形状。如果你已经有一套管用的自家格式，你不需要它。

## 有效的话应该是这样

- 它问收件人是谁、问你需要拿回什么，然后就不问了。要是它在问主题本身，这份 Skill 就跑偏了。
- 你列为"我需要拿回什么"的每一条，都能追溯到文件里的一个问题。
- 这些问题读起来是对准*收件人*知道的东西的，而不是你自己的开放问题原文抄录。
- 你可以把这个文件交给一个不在那场对话里的人，而他会明白自己为什么收到它、该在什么时候之前回复。
- 拿回来的答案能直接喂给新一轮追问，而不是变成一堆新问题。

## 它在整体中的位置

`to-questionnaire` 是一个随时可以拿起来用的独立 Skill。在你自己的知识到此为止、下一步是去问另一个人而不是再跑另一份 Skill 的地方用它。这最常发生在流程中途：规划卡在了某件不归你决定的事上。

它的邻居是 [grill-me](https://aihero.dev/skills-grill-me)，两者的区别在于答案住在谁那里。追问从你这里取答案；问卷从别人那里取答案。把拿回来的东西喂进新一轮追问，或者，如果这项工作要走向构建，就喂进 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec)。拿不准这一刻哪份 Skill 合适时，[ask-matt](https://aihero.dev/skills-ask-matt) 给你路由。
