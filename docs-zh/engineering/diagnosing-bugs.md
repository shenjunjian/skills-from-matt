## 它做什么

`diagnosing-bugs` 对一个难缠的 bug 或一次性能回退跑六个阶段的诊断：搭出复现、把它缩小、给假设排序、插桩、用回归测试修复、然后清理。

在一个**紧**的反馈回路存在之前，它不让 agent 形成理论：一个具名的命令，已经跑过一次，能在*这个* bug 上变红、修好之后变绿。拿到一份 bug 报告，一个 coding agent 的默认做法是读代码然后猜。这个 Skill 把这条路堵住。如果没有任何能变红的命令，就没有 Phase 2。这一道闸门就是这个 Skill 存在的意义。回路一旦存在，后面的每一步（二分、验证假设、插桩）都是机械活。

## 什么时候找它

输入 `/diagnosing-bugs`，或者当一个任务对得上时 agent 会自己找上它。它由 model 调用，在 "diagnose" 或 "debug this" 上触发，也在报告说某个东西坏了、在抛异常、在失败、或者很慢时触发。

把它留给难的：一眼看不出来的 bug、时有时无的 flake、在两个已知良好状态之间引进的回退。它慢且彻底，这是刻意的，所以对一个你想在一轮回复里得到答案的问题，它是错的工具。

| 你的情况 | 该去哪 |
| --- | --- |
| 一个你能用症状描述出来的具体缺陷 | 本 Skill |
| 一个慢的端点，或者一次有明确前后对照的时间回退 | 本 Skill。它有一条性能分支（先量基线，再二分） |
| "这个代码库的瓶颈在哪？"，没有具体症状 | 不是本 Skill。它诊断一个已知的失败，不做审计 |
| 别人给的一份原始 bug 报告，还没确认也没整理 | 先走 [triage](https://aihero.dev/skills-triage) |
| 为了回答一个设计问题写的丢弃式代码，不是追缺陷 | [prototype](https://aihero.dev/skills-prototype) |
| 以测试先行构建一个计划好的行为 | [tdd](https://aihero.dev/skills-tdd) |
| bug 修好之后，问当初什么能防住它 | [retro](https://aihero.dev/skills-retro)，在同一场 session 里跑 |
| 没有合适的 seam 能把这个 bug 锁住 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)，由你自己启动 |

## 紧的回路就是这个 Skill

Phase 1 拿走的力气最多，因为它是唯一真正难的阶段。这个 Skill 列出了搭出回路的办法，大致按推荐顺序：

1. 在能触及这个 bug 的那个 seam 上写一个失败的测试。
2. 对着跑着的 dev server 写一个 curl 或 HTTP 脚本。
3. 一次 CLI 调用配一个 fixture 输入，跟已知良好的快照做 diff。
4. 一个 headless browser 脚本，断言 DOM、console 或网络。
5. 一次抓包回放：一份存下来的请求、payload 或事件日志，单独跑过那段代码路径。
6. 一个丢弃式的壳子：系统的一个最小子集，一次函数调用。
7. 一个 property 或 fuzz 循环，用在"输出偶尔不对"上。
8. 一个可以交给 `git bisect run` 的二分壳子。
9. 一个差分回路：同样的输入，旧版本对新版本。
10. 一个 [human-in-the-loop](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop)（人在回路中）的 bash 脚本，最后手段。为此 Skill 随包提供 `scripts/hitl-loop.template.sh`：agent 跑这个脚本，你在终端里按提示操作，你的回答作为可解析的输出回到它手上。

有一个*回路*不是目标。**紧**才是：快（以秒计）、确定（每次跑结论一致）、锋利（断言你那个确切的症状，不是"没崩"），并且 agent 不需要你也能自己跑。一个 30 秒、结论会飘的回路，几乎不比没有好多少。对只在某些时候现身的 bug，目标不是一份干净的复现，而是**更高的复现率**：循环触发它、并行化、加压、注入 sleep，直到 flake 率高到可以拿来调试。

当 agent 搭不出回路时，这个 Skill 让它停下来明说，列出它试过的东西，并向你要 [environment](https://www.aihero.dev/ai-coding-dictionary/environment)（环境）访问权、一份抓下来的产物，或者授权它加临时插桩。它绝不能不顾这些继续去形成假设。

## 阶段之间的闸门

这些阶段是闸门，不是一份清单。某个条件成立之前，agent 不能进入那个阶段。

| 闸门 | 必须成立的条件 |
| --- | --- |
| 进入 Phase 2 | 一个具名的命令，已经跑过并且连同输出贴了出来，且能在这个 bug 上变红 |
| 进入 Phase 3 | 复现已经复现*并且*已经缩小：剩下的每一个元素都是复现这个 bug 所必需的 |
| 进入 Phase 4 | 存在 3-5 个已排序、可证伪的假设，每个都写明自己的预测，且在动手验证任何一个之前先给你看 |
| 进入 Phase 5 | 探针各自对应一个具体预测，一次只动一个变量，每条调试日志都带一个像 `[DEBUG-a4f2]` 这样的标签，于是一次 grep 就能把它们全找出来清理 |
| 完成 | 最初的复现已不再复现，插桩已经清干净，并且 commit message 点名了最终被证实的那个假设 |

Phase 5 有一个例外。agent 在修复之前先写回归测试，但只在存在一个**正确的 seam** 时才这么写：那个 seam 上测试能跑到调用处实际发生的真实 bug 模式。唯一可用的 seam 太浅时，这个 Skill 让 agent 直说这一点，而不是写一个给人虚假信心的测试。缺失的 seam 本身就是一个发现，agent 要把它记录下来，而不是藏起来。

## 常见问题

**在一些我只想直接要个答案的快问题上它也触发了。**
这是这个 Skill 被报告最多的问题。在 GPT-5.6-Sol 上尤其明显，用户报告它会在一个平淡的问题描述上触发："模型转而去触发那份相当正式的 diagnosing-bugs Skill。然后它接着构造了一个复现场景（通常是搭一个价值有限的 mock 场景），才给我一个回复或建议。这带来了明显的回复延迟。"有四个人在 [issue #578](https://github.com/mattpocock/skills/issues/578) 上报告了同一个问题。被接受的修法是先用更轻的做法，只在问题确实需要时才转入完整诊断，但这个改动还没发布。这份 Skill 是按 Claude Code 的调用行为调的，而 [model](https://www.aihero.dev/ai-coding-dictionary/model)（模型）激活门槛更低的那些会过于频繁地触发它。在这个修复发布之前，绕法是把你要什么说清楚（"就直接回答这个，别诊断"），或者在你的 [harness](https://www.aihero.dev/ai-coding-dictionary/harness)（运行环境）里为它关掉 model 调用。

**我能把它指向一个代码库，问性能问题都在哪吗？**
不能。它诊断你已经点得出名字的那一个失败。它的性能分支是给有症状的回退用的（先建立一个基线测量，然后二分，先测量后修复），不是给主动扫描用的。有人[提过一个做主动版本的 Skill 并被关掉了](https://github.com/mattpocock/skills/issues/431)；目前没有 Skill 干这事。

**它在动手写修复之前会停下来问我吗？**
不会。只有 Phase 3 有人工检查点：排好序的假设清单会在验证任何一个之前先给你看，你要是人不在，agent 就照自己的排序继续。插桩和修复之间没有闸门，所以 agent 可以在你还没认可它的根因结论之前就开始写代码。[Issue #124](https://github.com/mattpocock/skills/issues/124) 要求加那道闸门，仍然开着。你想要这道闸门的话，在调用这个 Skill 时说清楚。

**这个 bug 报告我已经跑过 `/triage` 了。这算不算同一件活做两遍？**
部分算，而两份 Skill 都没提这点。有位读者说过："Triage 的第 3 步本质上就是 diagnosing-bugs Phase 1-2 的一个浅层、有界的版本，可两份文件都没提到对方。"Triage 做的是一次有界的"这到底是不是 bug，问题面有多大"巡查；本 Skill 做的是彻底的那一版。先跑 triage 不算白费，因为它的核实常常把 Phase 1 的大部分原料给你交回来。但要预期本 Skill 会把那部分完整地重做一遍，也别指望有任何交叉引用会告诉你这一点。

**它贴出来的复现输出会不会泄漏密钥？**
可能会。这个 Skill 让 agent 把调用命令和它的输出贴出来，还要它去要 HAR 文件、日志转储、core 转储这类产物。没有任何指示让它把它们脱敏。[Issue #674](https://github.com/mattpocock/skills/issues/674) 提的正是这件事（凭据、token、cookie 和个人数据被复制进聊天、工单或 PR），并提出一条脱敏护栏。它还开着，也没实现。眼下把脱敏当成你自己的活，尤其在输出要流去任何公开的地方之前。

**我的安全扫描器把这个 Skill 标成了高风险。**
Snyk 会标，而这条标记是误报。它是整个集合里唯一随包附带一份可执行 shell 脚本（`hitl-loop.template.sh`）、并同时给出运行它的指示和 curl 一个 dev server 的指示的 Skill。一个随包的 `.sh` 文件、运行它的指示、加上对外 HTTP，这三样凑齐就足以触发静态扫描器。那个脚本本身不过是 30 行上下的 `read -r -p` 提示，为的是停下来等人工输入。扫描器评的是这个 Skill 可能做什么，不是被证实的漏洞利用。

**`/diagnose` 怎么了？**
v1.0.0 把它改名为 `/diagnosing-bugs`。旧名字已经不存在了。任何把 `/diagnose` 串起来的东西（你的一层包装 Skill、一个存下来的提示）都需要更新。

## 有效的话应该是这样

- 它在给出任何一个理论之前，先让你看到一个命令和它的红色输出。理论先到，说明这个 Skill 没在跑。
- 它复现的那个失败就是你报的那个，不是路上顺手发现的邻近问题。
- 它在开始猜之前先缩小复现，并且能说清剩下的每一块为什么必需。
- 它在验证任何一个假设之前，给你看一份 3-5 个假设的排序清单，每个都带着一个你可以证伪的预测。
- 它加的每条调试日志都带着一个像 `[DEBUG-a4f2]` 的标签，而它宣布完成时，用那个标签 grep 已经查不到东西。
- commit 或 PR 的 message 点名了哪个假设是对的。
- 当它没法用测试把这个 bug 锁住时，它直说，而不是写一个浅层的了事。

## 它在整体中的位置

`diagnosing-bugs` 是一个随时可取的独立项。有东西坏了你就启动它，修复和它的回归测试落地它就结束。它不保存任何状态，也不需要事先配置。[ask-matt](https://aihero.dev/skills-ask-matt) 把"有东西坏了"路由到这里。

有两个邻居要紧。[retro](https://aihero.dev/skills-retro) 排在它后面：修复落地之后，在同一场 session 里跑它，问当初什么能防住这个 bug，此时 session 手里的信息比一开始更多。`diagnosing-bugs` 从不自己调用 `retro`，因为 `retro` 由用户调用。[triage](https://aihero.dev/skills-triage) 对那些以别人的原始报告形式到来的 bug 排在它前面，并且对同样的头两个阶段做一次更浅的版本。
