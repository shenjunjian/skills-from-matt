## 它做什么

`prototype` 写出**用来回答一个问题的临时代码**：这个状态模型对不对，或者这个界面该长什么样。问题先行，由它决定你构建什么。回答错了问题的原型就是浪费，不管它看起来多好。

临时是对代码*写法*的约束，不是销毁它的承诺。不写测试，除了让它跑起来之外不做错误处理，不做抽象，不做持久化，因为这些对你想学会的那一件事都没有帮助。有两样东西留下来。答案进入真实代码，原型放进一个从 main 拉出的分支，作为答案的证据。

## 什么时候用它

输入 `/prototype`，或者当任务合适时 [agent](https://www.aihero.dev/ai-coding-dictionary/agent)（智能体）会自动用它。

一碰到无法靠讨论定下来的问题就立刻用它：一台边界情况多到脑子里装不下的状态机，一个不并排看到三个版本就想象不出来的界面。[Grilling](https://www.aihero.dev/ai-coding-dictionary/grilling)（拷问）会在这类问题上越拖越长。agent 换个说法重问，你靠猜，范围随之扩大。停下拷问，把临时版本搭出来，看一眼，然后用一行话给出答案。反过来，如果已经建好的东西行为不对、你想知道原因，用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)；做原型探索的是该构建什么，不是已构建的东西为什么坏。

你也会不请自来。[wayfinder](https://aihero.dev/skills-wayfinder) 会在它的地图上登记 `prototype` 类型的 Decision [ticket](https://www.aihero.dev/ai-coding-dictionary/ticket)（决策工单），你用这个 Skill 处理其中一张。

## 两条分支

问题决定走哪条分支，两条分支产出不同的东西：

- **"这个逻辑／状态模型对不对？"**：一个**可分享的单 HTML 文件**。一个自包含页面，不需要构建、不需要服务器，双击就能打开。它带一个有标注的状态面板，每次点击后重新渲染；带随意操作的按钮，可以按任意顺序试探模型；还带分标签页的**引导演练**（每个标签页一个场景，下面按顺序列出该点的按钮）。全部用领域语言标注，所以你可以把它交给设计师、PM 或领域专家，让他们自己试这个模型。页面背后的逻辑是一个小的纯模块（一个 reducer、一台状态机、一组函数），里面没有 DOM 代码，因此验证过的版本可以直接搬进真实代码。
- **"这该长什么样？"**：在一条路由上做出几个**差异极大**的 UI 变体，通过一个悬浮底栏和一个 `?variant=` URL 参数切换。变体之间必须在结构上有分歧，而不是在颜色上；三个只做小改动的卡片网格回答不了任何问题。它们尽可能渲染在真实页面里，对着真实数据和真实密度，因为在一个空白页面上评判的变体永远看着都行。

两条分支都把状态放在内存里，零配置启动，每一步之后展示完整状态。一旦你发现自己开始给某个原型加固（加测试、接真实数据库、为以后可能用到的情况做泛化），你就已经不在做原型了。

## 原型是一手资料

一个做完的原型留下两样东西，它们去不同的地方。

你把**答案**（结论加上它解决的问题）记录在某个持久的地方：一条 commit message、一个 ADR、实现工单。main 保留答案，在真实代码里。

**原型**是答案来源所在的可运行证据，不要删除它。它也不该进 main，因为没人维护它，而且它很快就过期。所以你把它提交到一个从 main 拉出的一次性 `prototype/<name>` 分支，永不合并，并在实现工单上留下指向那个分支的 [context pointer](https://www.aihero.dev/ai-coding-dictionary/context-pointer)（上下文指针）。main 保持干净，下一个接手工作的人能找到并重新运行原型。

## 常见问题

**等等，原型不是应该删掉吗？**
现在不了。以前是：搭出来，留下答案，把代码扔掉。对这种做法最有力的反对不在于速度。而在于*下一个 [session](https://www.aihero.dev/ai-coding-dictionary/session)（会话）是谁接手这项工作，他们手上有什么可以依据？*用散文摘要一个原型，会丢掉让它令人信服的那样东西。所以这个 Skill 现在把原型当作[一手资料](https://www.aihero.dev/ai-coding-dictionary/primary-source)。它落在从 main 拉出的 `prototype/<name>` 分支上，实现工单指向它。改变的是代码住在哪，不是纪律；它依然永不合并进 main。

**它以前会做一个终端应用。那去哪了？**
逻辑分支现在改为输出一个可分享的单 HTML 文件。终端应用只能由那些已经克隆了仓库、装好运行时来的人操作，而这恰恰把原型需要其意见的人排除在外：设计师、PM、知道状态模型该是什么意思的领域专家。一个双击就打开、被邮件转发之后仍然能用的自包含文件，谁都能操作。底下的纯逻辑模块没有变，它仍然是你搬进真实代码的那部分。

**该实现的时候，agent 却让我 `/prototype`。**
这是一个已知的命名问题。一个不了解整套流程的 agent，在工单已经存在时，会把 `prototype` 这个宽泛而吸引人的词读成"明显的下一步"。所以即使在那些设计已经在对话里定下来的场合，agent 也会点名推荐它。如果你已经知道要构建什么，下一步是按工单执行 `/implement`。只有当某个具体的设计问题悬而未决、而且讨论也解决不了时，才用原型。

**在构建任何生产功能之前，我是不是该把整个应用做成原型（比如给潜在客户演示）？**
那是另一种东西，只是恰好和这个 Skill 同名。这里说的原型范围限于一个问题，而"整个应用是什么"不算一个问题。全应用原型没有自然的停止点，于是它滑向变成生产应用：清理那一遍永远不会做，按原型规则写的代码（无测试、无错误处理）最终出现在用户面前。如果你需要销售演示，就刻意把它当作 demo 来构建，并明确说明其中没有一部分是生产代码。如果你需要定下一个设计问题，就把它削减到那一个问题。

**我怎么在独立的会话里运行它？**
原型待在自己的目录里，会产生大量你不想放进提问那个线程的 [context](https://www.aihero.dev/ai-coding-dictionary/context)（上下文），所以在别处运行它，只把答案带回来。用 [handoff](https://aihero.dev/skills-handoff) 把工作搬进那个会话，再把答案带回来。

**这不是烧 token 最快的方式吗？**
可能会，如果你为那些本可以靠讨论回答的问题做原型，或者让一个原型铺开成一个完整功能。真正要紧的比较不是 token 对零，而是 [tokens](https://www.aihero.dev/ai-coding-dictionary/token) 对比构建出错误的状态模型、并在它有了生产调用方之后才发现。把问题收窄、把运行缩短，开销就始终成比例。

## 起作用的表现

- 你能用一句话说出这个原型是为回答哪个问题而存在的，而且这句话写在 demo 顶部，不只在你脑子里。
- 不读代码的人也能操作逻辑 demo。他们打开文件，按引导演练标签页里的按钮，用自己的话描述看到的东西。
- 有人说"等等，这不该可能"或"咦，我一直以为是 X"。那是*想法*里的 bug，而这正是原型的目的。
- UI 变体在布局和信息层次上有分歧，不只是颜色和文案，你收到的反馈是"要 B 的页头配 C 的侧栏"。
- 一次坐下来就得到答案。一天之后你还在构建它，说明问题太大；拆开它。
- 结束时，main 里有这个决定、没有原型的任何部分，而实现工单指向仍然保存着原型的那个分支。

## 它在整体中的位置

`prototype` 是一个**随手可用的独立 Skill**：你用它定下一个设计问题，然后回去继续自己的工作。另一个 Skill 也会调用它。

调用它最多的是 [wayfinder](https://aihero.dev/skills-wayfinder)。wayfinder 地图由 **决策工单** 组成，`prototype` 是工单的四种类型之一：当卡住的问题是"这该长什么样"或"这该有什么行为"、多少讨论都解决不了时，就用它。讨论含糊的时候，wayfinder 会造出一个具体的东西供大家回应，而构建那个东西的就是这个 Skill。答案解决一张原型工单，地图把这个原型作为资产链接进去。

其余邻居在这件事的上游和下游。[grill-me](https://aihero.dev/skills-grill-me) 和 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 回答可拷问的问题；不可拷问的问题改来这里，而那一行答案送回访谈里。在下游，经过验证的状态模型或 UI 方向成为 [to-spec](https://aihero.dev/skills-to-spec) 的确定输入，to-spec 可以直接内联原型产出的那段富含决策的片段，而不是用散文描述它。其他情况，[ask-matt](https://aihero.dev/skills-ask-matt) 会在整套 Skill 里给你指路。
