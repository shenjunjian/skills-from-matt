用户请求做一次**回顾**（retrospective）。你要提出对编码 agent **环境**的改进，让后续运行更好。

## 步骤

1. 调用 Skill（技能）工具，传入 `writing-for-agents`，取写作风格指南。

2. 阅读用户指定那次会话的一手资料。这可能意味着在本机上翻查会话日志。用户没有指定会话时，默认用当前这次。

3. 在下列类别中寻找可改进的候选项。

- **导航**：agent 找到正确文件有多容易？文件之间是否存在隐藏依赖？加一个**导航指引**会不会更容易？_使用时机_：本次会话花了很长时间才找到某条信息。
- **自动化检查**：有没有哪些自动化检查能拦住 agent 犯的错？lint、类型检查、测试、文件系统检查器？先读仓库自己的检查命令（它的 `package.json`/构建工具的 `lint`/`check` 脚本、它的 CI workflow），这样"检查本来就有，只是没接上或者悄悄坏了"才是结论，而不是重新造一个。仓库没有**护栏**（既没有 pre-commit hook，也没有跑 lint/typecheck/test 命令的 CI job），这本身就是结论：没有 lint 的仓库是一直被错过的机会，不是中性的默认状态。_使用时机_：agent 犯了自动化检查本可以拦住的错，或者仓库根本没有护栏。
- **编码规范**：是否该给**评审 agent**加一条新规则去执行？是否该删除或澄清某条现有规则？先给违规分类：**机械型**违规（固定的语法模式、禁用的 API、import 的形式、文件位置规则）一律交给确定性检查，没有别的办法：在仓库自己的 linter 里加自定义规则、新增 pre-commit hook，或新增 CI job，按仓库语言和现有护栏选最省事的那个。默认先做检查，而不是先写规则。`CODING_STANDARDS.md` 只留给真正的**判断题**（跨文件一致性、"与周围代码风格一致"，任何护栏都替代不了的那些）。_使用时机_：评审 agent 没拦住某个错误。
- **全局 AGENTS.md**：有没有哪些引导指令本该改放进编码规范（或自动化检查）里？_使用时机_：AGENTS.md 文件特别大，在仓库里或者在用户的全局作用域里。
- **工具开销**：agent 有没有做出本可以精简的高开销工具调用？有没有哪个自建工具（CLI、MCP）特别浪费 token？_使用时机_：agent 做出了一次高开销的工具调用。
- **空转指令**：在引导文件里找出那些不会改变 agent 行为的指令。_使用时机_：引导文件又大又难用。
- **信息获取**：寻找能扩大 agent 信息获取面的机会。把 dev server 的日志 tee 出来，只读访问第三方服务。_使用时机_：某条关键信息 agent 拿不到。

4. 按严重程度排序，把这些候选项呈现给用户。

## 参考

### 实现与评审

记住，所有工作都经过两个阶段：实现和评审。实现 agent 承受的**上下文压力**最大。它负责探索、写代码、调试失败。

评审 agent 的上下文压力最小，它拿到的是一个 diff，不需要探索。它通常也不需要写代码或调试。

所以执行编码规范该由评审 agent 负责，而不是实现 agent。

### 文件

你可以访问仓库里的几个文件：

- `CLAUDE.md`/`AGENTS.md`：这些文件会被推进任何在本仓库工作的 agent 的上下文窗口。要用得极度节制，通常只用来做指向其他文件的**导航指引**。
- `CODING_STANDARDS.md`：这个文件在评审阶段读取，不在实现阶段。如果规范文件超过 1,000 行，就加**导航指引**指向 docs 目录。
- Docs：把 docs 当参考文件用，由其他文件指向它们。写新文档之前先找现有文档。
- Skills：用 skills 承载文档（因为它们的 description 会进入 agent 的上下文窗口），或者用作用户调用的命令。遵循 `writing-for-agents` 这个 skill 里的建议。
