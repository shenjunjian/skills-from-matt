# Triage（分诊）

把项目工单跟踪器上的工单推过一个小型分诊角色状态机。

如果本仓库把外部 pull request（拉取请求）视为一种请求入口（见 issue tracker 配置），那么分诊也覆盖它们：**PR 就是一个带着代码的工单**，用同样的角色、同样的状态、同样的状态机，只有下文标注"针对 PR"的几处差异。按 tracker 配置把单独的 `#42` 解析成工单还是 PR。

分诊期间发到 issue tracker 的每一条评论或工单，都**必须**以这句声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何写出经得起时间考验的 agent brief（代理简报）
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库如何运作

## 角色

两个**分类**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：需要维护者评估
- `needs-info`：等报告人补充信息
- `ready-for-agent`：规格完整，可交给 AFK agent（离线运行的 agent）
- `ready-for-human`：需要人来实现
- `wontfix`：不予处理

针对 PR，这些状态要对照附带的代码来理解：`ready-for-agent` 表示已附上 brief，agent 应在这个 diff 上走下一步；`ready-for-human` 表示可以交给人来合并。

每个已分诊的工单都应恰好带一个分类角色和一个状态角色。如果状态角色互相冲突，先标记出来并询问维护者，再做任何其他事。

以上是规范的角色名。issue tracker 里实际使用的标签字符串可能不同，映射关系应当已经提供给你。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

状态转移：一个无标签的工单通常先进入 `needs-triage`；从那里可以转到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告人回复之后，`needs-info` 回到 `needs-triage`。维护者可以随时覆盖；遇到看起来不正常的转移，先标记并询问，再继续。

## 调用方式

维护者调用 `/triage`，用自然语言说明自己想做什么。理解请求并执行。例如：

- "给我看看有什么需要我处理"
- "我们来看看 #42"（工单或 PR）
- "把 #42 移到 ready-for-agent"
- "哪些可以交给 agent 接手？"

## 展示需要关注的事项

查询 issue tracker，按三组呈现，最旧的排前面：

1. **无标签**：从未分诊过。
2. **`needs-triage`**：正在评估。
3. **`needs-info` 且报告人在上次分诊记录之后有新活动**：需要重新评估。

PR 在范围内时，把外部 PR 也纳入这三组，每行末尾标上 `[PR]` 或 `[issue]`。发现阶段只列出*外部* PR（tracker 配置定义了谁算外部），因此合作者正在推进的 PR 不属于分诊工作。这个过滤只作用于发现阶段；被明确点名的 PR 无论作者是谁都要分诊。

给出数量和每项一行的摘要。让维护者挑选。

## 分诊某个具体的工单或 PR

1. **收集上下文。** 通读整个工单或 PR（正文、评论、标签、作者、日期；针对 PR 还要看 diff）。解析已有的分诊记录，别重复问已经解决过的问题。用项目的领域术语表来探索代码库，并遵守该区域的 ADR（架构决策记录）。对照代码库跑两项检查：(a) **冗余检查**：按领域概念（不只是请求的措辞）搜索是否已有该行为的实现，并报告你查过哪些地方。若已找到，那就是"已实现"型的 `wontfix`（第 5 步）。(b) **既往拒绝检查**：读取 `.out-of-scope/*.md`，把与此请求相似的条目呈现出来。

2. **给出建议。** 告诉维护者你建议的分类和状态及理由，再附上代码库中与本请求相关的简要概述（包括它是否已经实现）。等待指示。

3. **核实说法。** 在任何 grilling（追问）之前，先确认这个说法站得住。是 bug 就照报告人给的步骤复现。是 PR 就确认 diff 做到了它声称的事：检出代码，运行相关测试或命令。报告结果：已确认（附代码路径）、失败，或细节不足（这是 `needs-info` 的有力信号）。一次确认过的核实能让 agent brief 有力得多。

4. **必要时 grilling。** 如果请求需要充实，调用 Skill 工具两次，分别用于 "grilling" 和 "domain-modeling"，一轮一轮地提问把它打磨成型，同时提炼领域术语，并在决策落定时就地更新 `GLOSSARY.md` 和 ADR。

5. **落实结果：**
   - `ready-for-agent`：发一条 agent brief 评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：结构与 agent brief 相同，但要写清为什么不能委派出去（需要判断、需要外部访问、需要设计决策、需要人工测试）。
   - `needs-info`：发分诊记录（模板见下）。
   - `wontfix`：关闭工单，评论内容取决于*原因*：
     - **已经实现**：改动在代码库里已经存在。指出它在何处；**不要**写入 `.out-of-scope/`（那个知识库是给被*拒绝*的请求用的，不是给已建成的功能）。
     - **拒绝（bug）**：礼貌地说明原因，然后关闭。
     - **拒绝（enhancement）**：写入 `.out-of-scope/`，在评论里链接过去，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用该角色。若有部分进展，可附一条评论。

## 快速覆盖状态

如果维护者说"把 #42 移到 ready-for-agent"，相信他们，直接应用该角色。先确认你打算做什么（角色变更、评论、关闭），再执行。跳过 grilling。若在没有 grilling 的情况下移到 `ready-for-agent`，问一下他们是否想写一份 agent brief。

## needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把 grilling 中解决掉的内容全部记到 "established so far" 之下，免得这些工作白做。问题必须具体、可行动，不能是"请提供更多信息"。

## 恢复上一次会话

如果这个工单或 PR 上已有分诊记录，先读它们，检查报告人是否回答了尚未解决的任何问题，然后在继续之前给出更新后的全貌。不要重复问已经解决过的问题。
