这个 skill 拿到当前对话的上下文和对代码库的理解，产出一份 spec。不要访谈用户，只把你已经知道的东西综合起来。

工单跟踪器和 triage 标签的用词表本应该已经提供给你。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

1. 探索仓库，理解代码库当前的状态（如果你还没做过）。在整个 spec 里使用项目领域词汇表中的用词，并遵守你所在改动区域的任何 ADR。

2. 勾勒出你打算用来测试这个功能的 seam。已有的 seam 优先于新的 seam。用尽可能高的 seam。如果确实需要新的 seam，在你能找到的最高点提出它。整个代码库里的 seam 越少越好 - 理想的数量是一个。

和用户确认这些 seam 是否符合他们的预期。

3. 用下面的模板写出 spec，然后发布到项目的工单跟踪器。打上 `ready-for-agent` 的 triage 标签 - 不需要额外的 triage。

<spec-template>

## Problem Statement（问题陈述）

用户面临的问题，从用户的视角来写。

## Solution（解决方案）

这个问题的解决方案，从用户的视角来写。

## User Stories（用户故事）

一份很长的、带编号的用户故事清单。每条用户故事使用这个格式：

1. 作为一名 <actor>，我希望有一个 <feature>，以便 <benefit>

<user-story-example>
1. 作为一名手机银行客户，我希望能在我的账户上看到余额，以便我能对自己的支出做出更明智的决定
</user-story-example>

这份用户故事清单要极其详尽，覆盖这个功能的方方面面。

## Implementation Decisions（实现决策）

一份已经做出的实现决策清单。可以包括：

- 将要构建/修改的模块
- 这些模块中将被修改的接口
- 开发者给出的技术澄清
- 架构决策
- schema 变更
- API 契约
- 具体的交互

不要写具体的文件路径或代码片段。它们很快就会过时。

例外：如果某次原型试验产出了一段代码，它比散文更精确地编码了一个决策（状态机、reducer、schema、类型形状），把它内联进相关的决策里，并简短注明它来自原型试验。裁剪到只包含承载决策的部分，不是一个能跑的演示，只要关键的片段。

## Testing Decisions（测试决策）

一份已经做出的测试决策清单。包括：

- 对"什么是好测试"的描述（只测外部行为，不测实现细节）
- 哪些模块会被测试
- 这些测试的先例（即代码库里类似的那些测试）

## Out of Scope（范围之外）

对这份 spec 范围之外的那些事情的描述。

## Further Notes（补充说明）

关于这个功能的任何补充说明。

</spec-template>
