# To Tickets

把一份计划、一份 spec 或一段对话拆解成一组**工单**：tracer-bullet 式的 vertical slice，每个工单声明是哪些工单**阻塞**了它。

工单跟踪器和 triage 标签的用词表本应该已经提供给你。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话上下文里已有的东西来干活。如果用户作为参数传入了某个引用（一份 spec 的路径、一个工单号或 URL），把它取回来，读完它的整个正文和评论。

### 2. 探索代码库（可选）

如果你还没探索过代码库，那就探索一遍，理解代码当前的状态。工单的标题和描述要使用项目领域词汇表中的用词，并遵守你所在改动区域的 ADR。

寻找可以提前重构代码的机会，让后续实现更容易。"先把改动变简单，再做那个简单的改动。"

### 3. 起草 vertical slice

把工作拆成 **tracer bullet** 工单。

<vertical-slice-rules>

- 每个 slice 切出一条窄但**完整**的路径，穿过所有层（schema、API、UI、测试）：是纵向的，不是某一层横着切一刀
- 一个完成的 slice 自己就能演示或验证
- 每个 slice 的体量控制在一个全新的上下文窗口里装得下
- 需要提前做的重构都先做掉

</vertical-slice-rules>

给每个工单配上它的**阻塞边**：哪些其他工单必须在它开始之前完成。没有阻塞者的工单可以立刻开始。

**大范围重构是 vertical slicing 的例外。** 一次**大范围重构**指的是一个机械性的改动（重命名一个列、改一个共享符号的类型），它的**波及面**散满整个代码库，一次编辑就同时打断成千上万个调用点，任何一个 vertical slice 都没法以绿色落地。别硬把它塞进 tracer bullet；按 **expand-contract** 排成序列。先 expand：把新的形式加在旧形式旁边，什么都不破坏。然后分批迁移调用点，批次大小按波及面来定（按包、按目录），每一批是它自己的工单、被 expand 阻塞，因为旧形式还在，所以批与批之间 CI 能保持绿色。最后 contract：当一个调用者都不剩时，删掉旧形式，这个工单被所有迁移批次阻塞。如果连单独一批都没法保持绿色，仍然保留这个序列，但让这些批次共用一个集成分支，并且它们全部阻塞最后一张 integrate-and-verify 工单；绿色只在那张工单上承诺。

### 4. 追问用户

把提出的拆分方案以带编号的清单形式呈现。对每个工单，展示：

- **标题**：简短、能说清事情的名字
- **Blocked by**：哪些其他工单（如果有）必须先完成
- **它交付什么**：这个工单让哪一段端到端的行为跑起来

问用户：

- 粒度合适吗？（太粗 / 太细）
- 阻塞边对吗：每个工单是不是只依赖那些真正卡住它的工单？
- 有没有工单应该合并或者再拆开？

反复迭代，直到用户认可这个拆分。

### 5. 把工单发布到已配置的跟踪器

发布已经批准的工单。**怎么发**取决于 `/setup-matt-pocock-skills` 配置的是哪个跟踪器；工单本身两种情况是一样的，变的只是阻塞边的形态：

- **本地文件** → 每个工单写一个文件，放在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md`，从 `01` 开始按依赖顺序编号（阻塞者在前）。每个文件的 "Blocked by" 列出它依赖的编号/标题。使用下面的单工单文件模板：一个文件一个工单，绝不写成一个大合集文件。
- **真实的工单跟踪器（GitHub、Linear，…）** → 按依赖顺序（阻塞者在前）每个工单发布一个 issue，这样每个工单的阻塞边就能引用真实的标识符。平台如果有原生的阻塞关系就用它；没有的话，就把每个工单的 "Blocked by" 设成那些阻塞它的 issue。如果来源是一个已存在的 issue，就把每个工单建成它的子 issue（见跟踪器文档里的 operation）。除非另有指示，否则打上 `ready-for-agent` 的 triage 标签；这些工单按构造就是 agent 可以直接领走的。

沿**前沿**推进：任何阻塞者都已完成的工单。对于一条纯线性的链，这就是从上到下。

不要关闭或修改任何父 issue。
