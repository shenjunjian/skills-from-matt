# UI Prototype（UI 原型）

在同一条路由上生成**几个截然不同的 UI 变体**，用一个悬浮底栏切换。用户在浏览器里来回翻看各个变体，挑一个（或者从每个里各偷一点），剩下的全部丢掉。

问题若是逻辑 / 状态，而不是某样东西长什么样，那就走错了分支。改用 [LOGIC.md](LOGIC.md)。

## 什么时候该用这个形态

- "这个页面该长什么样？"
- "这个仪表盘（dashboard）我想先看几个方案再定下来。"
- "给设置页面换个布局试试。"
- 凡是用户本来要花一天时间，在脑子里比较三张含糊的效果图的场合。

## 两种子形态：强烈倾向子形态 A

UI 原型在**跟应用其余部分贴在一起**时最好判断：真的页头、真的侧栏、真的数据、真的信息密度。一条孤立的一次性路由是真空：每个变体单独看都挺好。只要存在一条合理的现有页面可以承载这些变体，就默认用子形态 A。只有原型确实没有就近的安身之处时，才去用子形态 B。

### 子形态 A：改动一个已有页面（首选）

路由本来就存在。各个变体渲染在**同一条路由**上，由 `?variant=` 这个 URL 查询参数控制。现有的数据获取、路由参数和鉴权一概不动。只换渲染部分。这是默认；除非有明确理由，否则就选它。

原型要做的东西目前没有页面，但*自然会住在某个页面里*（仪表盘的一个新分区、设置页面的一个新卡片、已有流程里的新一步），那仍然算子形态 A。把各个变体挂到宿主页面里面。

### 子形态 B：一个新页面（最后手段）

只有当被做原型的东西确实没有可以栖身的现有页面时才用它（例如一个全新的顶层界面，或者一条没法嵌到任何合理位置的流程）。

按项目本来在用的路由约定，创建一条**一次性路由**。不要另造一套顶层结构。命名要一眼看出是原型（例如路径或文件名里带上 `prototype` 这个词）。同样用 `?variant=` 这套做法。

在决定用子形态 B 之前先自问一遍：真的没有哪个现有页面能把它嵌进去吗？一条空路由会掩盖掉一条有内容的路由所能暴露的设计问题。

两种子形态里，悬浮底栏完全一样。

## 流程

### 1. 写下问题并定下 N

默认**三个变体**。超过 5 个就不再截然不同，而是变成噪音，所以到此为止。

把方案写成一行，记在原型所在的位置或文件顶部注释里：

> "三个设置页面的变体，通过 `?variant=` 切换，挂在已有的 `/settings` 路由上。"

无论用户在场与否、能不能出声反对，这一行都管用。

### 2. 生成截然不同的变体

逐个起草每个变体。每个都要满足：

- 该页面的用途，以及它能拿到的数据。
- 项目的组件库 / 样式体系（TailwindCSS、shadcn、MUI、纯 CSS，无论哪一套）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**：不同的布局、不同的信息层级、不同的主要操作入口，而不只是不同的颜色。三张略作改动的卡片网格不算 UI 原型，那是壁纸。两个草稿出来太像，就带着明确的"不要用卡片网格"的指引重做其中一个。

### 3. 把它们串起来

在这条路由上建一个切换器组件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（已有页面）：切换器之上保留全部现有的数据获取；每个变体只换渲染出来的那棵子树。

子形态 B（新页面）：`/prototype/<name>` 下的这条一次性路由挂载同一个切换器。

### 4. 做出悬浮切换器

屏幕底部居中一个固定位置的小栏，三件东西：

- **左箭头**：切到上一个变体（到头环绕）。
- **变体标签**：显示当前变体的键名，变体若导出了名字，就一并显示。例如 `B (Sidebar layout)`。
- **右箭头**：切到下一个（到头环绕）。

行为：

- 点箭头会更新 URL 查询参数（用框架的路由方法，例如 Next 上的 `router.replace`、React Router 上的 `navigate` 等），这样变体既可分享又经得起刷新。
- 键盘：`←` 和 `→` 方向键也能切换。焦点在 `<input>`、`<textarea>` 或 `[contenteditable]` 上时不要拦截方向键。
- 与页面在视觉上明显区分（例如高对比度的胶囊形状、细微阴影），让人一眼看出它不属于被评审的设计。
- 生产构建里隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价判断做门控，这样误合了原型也不会把这一栏推给用户。

切换器做成一个共享组件，两种子形态都能复用。放在项目里共享 UI 所在的位置。

### 5. 交付出去

把 URL（以及 `?variant=` 的各个取值）告诉用户。他们会在自己方便的时候翻一遍。有价值的反馈通常长成**"我要 B 的页头配 C 的侧栏"**那样，而那才是他们真正想要的设计。

### 6. 记下答案并收尾

某个变体胜出之后，记下答案（哪个变体、为什么），再按 [SKILL](SKILL.md) 描述的方式保留原型。把胜出的那份折进真实代码，其余的挪到一次性分支上，而不是留在 main：

- **子形态 A**：把胜出的那份折进已有页面；从 main 删掉落选的变体和切换器。
- **子形态 B**：把胜出的变体提升成一条真实路由；从 main 删掉那条一次性路由和切换器。

完整的变体集合就是一手素材，所以它落在一次性分支上，而不是垃圾桶里；而留在 main 分支里的变体组件和切换器很快会腐烂，并让下一个读代码的人困惑。

## 反模式

- **变体之间只差颜色和文案。**那是微调，不是原型。真正的变体在结构上有分歧。
- **变体之间共享太多代码。**共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就把目的抵消了。每个变体都应该可以自由地把布局扔掉。
- **把变体接到真实的写操作上。**只读原型挺好。某个变体确实需要改动数据时，让它指向一个占位实现：问题是"这该长什么样"，不是"后端能不能跑通"。
- **把原型直接提升到生产。**变体代码是在原型约束下写的（没有测试、错误处理只做最低限度）。折进真实代码时按正规写法重写它。
