# Logic Prototype（逻辑原型）

一个独立自包含的 HTML 文件（一份**可分享的演示**），让任何人靠点按钮就能驱动一个状态模型。问题关乎**业务逻辑、状态转移或数据形状**时用它：这类东西写在纸面上看着合理，只有真拿实际用例推一遍才会觉得不对。

因为它只有一个文件、什么都不用装，你可以把它交给非开发者（设计师、PM、领域专家），让他们自己去感受这个模型。所以它说的是他们的语言，而不是代码的语言。

## 什么时候该用这个形态

- "我不确定这个状态机能不能处理先 X 再 Y 这种边界情况。"
- "这个数据模型真的能表达这样一种情形吗……"
- "动手写 API 之前，我想先摸出它该长什么样。"
- 任何人想要**按下按钮、看状态变化**的场合。

如果问题是"这东西该长什么样"，那就走错了分支。改用 [UI.md](UI.md)。

## 流程

### 1. 写下问题

动手写代码之前，先把你原型的是哪个状态模型、要回答哪个问题写下来。一段话，放在演示的开头（写在看得见的引言里，而不只是注释）。逻辑原型答错了问题就是纯浪费，所以把问题写明，好在事后核对，无论用户是此刻在场，还是离开之后回头再看。

### 2. 把逻辑隔离进一个可移植的模块

把真正的逻辑（回答问题的部分）放进单个 `<script>` 块，写成一个小的纯模块，将来可以整个摘出来丢进真实代码库。页面外壳是用完即弃的，这个模块不是。

合适的形状取决于问题：

- **一个纯 reducer**：`(state, action) => state`。action 是离散事件、state 是单个值时合适。
- **一个状态机**：显式的状态和转移。当问题里包含"此刻哪些 action 才是合法的"时合适。
- **一小组作用于普通数据类型的纯函数**。没有隐含的当前状态、只有各种变换时合适。
- **一个带有清晰方法表面的 class 或模块**，当逻辑确实掌管着持续的内部状态时。

挑最贴合所提问题的那个形状，*而不是*最容易接到页面上的那个。保持纯粹：不碰 DOM，不碰 `document`，不要有按钮处理函数伸进它内部。页面调用它；任何东西都不反向流动。这正是原型能活过自身寿命的原因：问题一旦有了答案，经过验证的那个 reducer / 状态机 / 函数集合就能自己搬进真实的模块。

### 3. 构建这个可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS：不用框架、不用打包器、不用服务器，全部内联，所以双击就能打开，也能被邮件转来转去而不失效。任何人都能靠打开它跑起来。

写给非开发者看。每个标签都用**领域语言**，不是代码：按钮和状态读起来像业务，不像代码里的 reducer。用平白的文字解释正在发生什么。

版面按清晰的层级从上往下排：

1. **标题加一句话说明**，讲清这个演示能让你探索什么（第 1 步里的那个问题）。
2. **当前状态**：把完整的相关状态渲染成一块可读的面板（带字段标签，不是一坨原始 JSON），每次点击后重新渲染，让变化看得见。对非开发者跟不上的地方，就点明刚刚改了什么。
3. **自由操作按钮**：一个 action 一个按钮，始终可用，任何人都能按任意顺序拨弄这个模型。每次点击派发对应的 action 并重新渲染状态。
4. **引导式走查**：一组 **scenario（场景）**，一个标签页一个。每个标签页顶部用平白的话简述这个场景（它摆出什么局面、要看什么），下面列出该场景要按的**按钮顺序**。每一步都是一个真按钮：点它就执行那个 action 并进入下一步。开始一次走查会重置到某个已知的初始状态，所以场景每次跑起来都一样。

挑那些演示别扭情况的场景，纸面上难以推理的那些：顺利路径、一个棘手的边界情况、试着做一次本该非法的操作。

做得好看但要克制：干净的排版、宽松的留白、一种强调色。不做动画，不做花活：任何跟状态和按钮抢注意力的东西都不要。

### 4. 交付出去

把文件发给他们，或者替他们打开。他们会在自己方便的时候点一遍走查和自由操作；有价值的时刻出现在他们说"等等，这不该能发生"或者"咦，我以为 X 会不一样"的时候；那是**想法**里的 bug，而这正是整件事的目的。他们想要新的 action 或新的场景，就加上。原型是逐步演进的。

### 5. 记下答案并保留原型

原型回答完它的问题之后，先记下答案，再按 [SKILL](SKILL.md) 描述的方式保留原型。逻辑这边对应的做法：经过验证的 reducer / 状态机 / 函数集合搬进真实模块（这个决策被吸收）；HTML 外壳跟着进那个保留原型作为一手素材的一次性分支；因为它是一个自包含文件，在那里照样轻易可重跑。

## 反模式

- **别加测试。**一个需要测试的原型就不再是原型了。
- **别接真实数据库。**用内存状态，除非问题正是关于持久化。
- **别做泛化。**不要"万一以后要支持 X 呢"。原型只回答一个问题。
- **别把逻辑和页面搅在一起。**纯模块若引用了 DOM、`document` 或按钮处理函数，就没法摘出来了。页面保持为纯模块之上的一层薄壳。
- **别上手框架、打包器或服务器。**接收者双击一个文件就行；一个 React 应用或开发服务器会毁掉"可分享"。
- **别把 HTML 外壳带进生产环境。**这页代码是为了让人手动点着看而写的。背后的那个逻辑模块才是值得留下的部分。
