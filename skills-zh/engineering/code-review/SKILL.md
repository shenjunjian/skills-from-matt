对 `HEAD` 与用户给出的一个定点之间的 diff 做双轴评审：

- **Standards**：代码是否遵循本仓库成文的编码标准？
- **Spec**：代码是否忠实实现了源头的工单 / spec？

两根轴都作为**并行的 sub-agent** 运行，这样它们不会污染彼此的上下文，然后本 Skill 汇总它们各自的发现。

工单跟踪器应当已经提供给你了。如果没有，告诉用户去跑 `/setup-matt-pocock-skills`。

## 流程

### 1. 钉住定点

用户说的那个就是定点（一个 commit SHA、分支名、tag、`main`、`HEAD~5` 等）。如果没说，向他索要。

把 diff 命令确定下来，只用一次：`git diff <fixed-point>...HEAD`（三点，于是比较是相对 merge-base 做的）。另外用 `git log <fixed-point>..HEAD --oneline` 记下 commit 清单。

再往下走之前，先确认这个定点能解析（`git rev-parse <fixed-point>`）并且 diff 非空。错误的 ref 或空的 diff 该在这里就失败，而不是在两个并行的 sub-agent 里面失败。

### 2. 找出 spec 来源

按这个顺序找源头的那份 spec：

1. commit 信息里的工单引用（`#123`、`Closes #45`、GitLab 的 `!67` 等），通过跟踪器文档里的那套工作流取回。
2. 用户作为参数传进来的一个路径。
3. `docs/`、`specs/` 或 `.scratch/` 下某个与分支名或功能对得上的 spec 文件。
4. 什么都没找到，就问用户 spec 在哪。他说没有，那么 **Spec** sub-agent 就跳过，并回报"no spec available"。

### 3. 找出标准来源

在仓库里搜遍所有记录"代码该怎么写"的文件。只要 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md` 存在，它们就必须进这份清单。

除仓库自己成文的那些之外，Standards 这根轴始终还带着下面这份**坏味道基线**：一组固定的 Fowler code smells（坏味道）（出自 _Refactoring_ 第 3 章），即便某个仓库什么都没成文也照样适用。有两条规则约束它：

- **仓库优先。** 一条成文的仓库标准总是胜出；在它认可某样基线本会指出的东西时，按下这条坏味道。
- **永远是靠判断的取舍。** 每种坏味道都是一个带标签的启发式（"可能是 Feature Envy"），从来不是硬性违规。和这里任何标准一样，工具链已经在强制执行的那些一律跳过。

每种坏味道都写成*它是什么* → *怎么修*；拿它去比对 diff：

- **Mysterious Name**（神秘命名）：一个函数、变量或类型，名字看不出它在做什么或装着什么。→ 改名；想不出一个诚实的名字，说明设计本身浑浊。
- **Duplicated Code**（重复代码）：同一种逻辑形状在这次改动里出现在不止一个 hunk（补丁块）或不止一个文件里。→ 把共同的形状抽出来，两处都调它。
- **Feature Envy**（依恋情结）：一个方法伸手取别的对象的数据，比取自己的还多。→ 把这个方法搬到它所依恋的数据上。
- **Data Clumps**（数据泥团）：同样那么几个字段或参数总是一起动（一个急着出世的类型）。→ 把它们收进一个类型，传那个类型。
- **Primitive Obsession**（基本类型偏执）：用一个基本类型或字符串去顶替一个本该有自己的类型的领域概念。→ 给这个概念一个自己的小类型。
- **Repeated Switches**（重复的 switch）：对同一个类型的同一种 `switch`/`if` 级联，在这次改动里反复出现。→ 换成多态，或者换成两处共用的一张 map。
- **Shotgun Surgery**（霰弹式修改）：一次逻辑上的改动迫使 diff 里散落着对许多文件的编辑。→ 把一起变的东西归拢到一个模块里。
- **Divergent Change**（发散式变化）：一个文件或模块因为几个互不相关的原因被改。→ 拆分，让每个模块只因一个原因而变化。
- **Speculative Generality**（夸夸其谈通用性）：为 spec 里并不存在的需求加了抽象、参数或钩子。→ 删掉；内联回去，直到真需求出现。
- **Message Chains**（过度消息链）：`a.b().c().d()` 这种调用方不该依赖的长距离导航。→ 把这段行走藏进第一个对象的一个方法后面。
- **Middle Man**（中间人）：一个基本只在往后转发的类或函数。→ 砍掉，直接调真正的目标。
- **Refused Bequest**（被拒绝的遗赠）：一个子类或实现者无视或覆盖了它继承来的大部分东西。→ 丢掉继承，改用组合。

### 4. 并行起两个 sub-agent

两个 sub-agent 调用一起发出，在前台，然后汇总它们返回的报告。

**Standards sub-agent 的 prompt** 应当包含：

- 完整的 diff 命令和 commit 清单。
- 你在第 3 步找到的标准来源文件清单，**外加第 3 步那份坏味道基线**整份粘进去（sub-agent 没有别的途径拿到它）。
- 任务说明："按文件、必要时按 hunk 汇报：(a) diff 违反某条成文标准的每一处，引出具体的标准（文件 + 那条规则）；(b) 你发现的任何基线坏味道，说出它的名字并引用那个补丁块。区分硬性违规与靠判断的取舍：违反成文标准可以算硬性，基线坏味道永远只是靠判断的取舍，而成文的仓库标准压过基线。工具链已在强制执行的那些一律跳过。全文 400 词以内。"

**Spec sub-agent 的 prompt** 应当包含：

- diff 命令和 commit 清单。
- spec 的路径，或者取回的内容。
- 任务说明："汇报：(a) spec 要求过但缺失或只做了一半的需求；(b) diff 里没被要求过的行为（范围蔓延）；(c) 看起来实现了、但实现方式看着就不对的需求。每条发现都引用 spec 的原文那一行。全文 400 词以内。"

如果 spec 缺失，就跳过 Spec sub-agent，并在最终报告里写明这一点。

### 5. 汇总

把两份报告分别放在 `## Standards` 和 `## Spec` 这两个标题下呈现，原样或者稍作清理。**不要**合并发现，也不要重排它们的次序，因为这两根轴是刻意分开的（见 _为什么要两根轴_）。

末尾给一行总结：每根轴各有多少条发现，以及**每根轴内部**最严重的那一个问题（若有）。不要跨轴选出一个总冠军：那正是这层分隔要阻止的重排。

## 为什么要两根轴

一次改动可能过了一根轴却栽在另一根上：

- 代码遵循了所有标准，但实现的是错的东西 → **Standards 通过，Spec 失败。**
- 代码做的正是工单要求的，却破坏了项目惯例 → **Spec 通过，Standards 失败。**

把它们分开汇报，能防止一根轴盖住另一根轴。
