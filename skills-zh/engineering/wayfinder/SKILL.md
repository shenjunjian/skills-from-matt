一个模糊的想法到来了：它太大，一个智能体会话装不下，还笼罩在雾里，从这里到**目的地**的路还看不见。寻路（wayfinding）要找的是这条路，不是朝目的地猛冲。这个 Skill 把这条路画成仓库工单系统上的一张**共享地图**，然后一次一张地处理它的 **Decision ticket**（决策工单，也就是解决结果是决策的问题，不是要执行的构建切片），直到路线清晰。

目的地因项目而异，而给它命名是绘制地图的第一个动作：它塑造每一张工单。它可能是一份要交接出去、再反复打磨的 spec（规格说明），一个在规划开始前就要定下来的决策，也可能是一处就地完成的改动，比如数据结构的迁移。这张地图不挑领域：工程工作、课程内容，凡是套得上这个形状的都行。

## Plan, don't do（只规划，不动手）

Wayfinder 默认是**规划**：每张工单解决一个决策，地图做完的时候路已经清楚，在别人动手做那件事之前没有剩下要定的事。那种"干脆把工作做掉"的冲动，通常就是信号：你已经走到地图边缘，该交接了。一个项目可以在自己的 **Notes**（备注）里覆盖这条默认，把执行也纳入地图；但如果没有，就产出决策，不产出交付物。

## Refer by name（用名字指代）

每张地图、每张工单，在跟踪器里都是一条 issue（工单），所以它们各有一个**名字**：自己的标题。在人会读到的一切东西里（叙述文字、地图的 Decisions so far（已有决策）），都用这个名字指代它，绝不用光秃秃的 id、编号或 slug。满屏的 `#42, #43, #44` 读不了；名字一眼就认得出。id 和 URL 并没有消失；名字包住它的链接，但它们待在名字_里面_，不能顶替名字。

## The Map（地图）

地图是本仓库工单系统里的单个工单，打上 `wayfinder:map` 标签，它是正式的产出物。它的工单是地图的子工单。

地图是一份**索引**，不是存储。它列出已经做出的决策，并指向装着这些细节的工单；一个决策只活在一个地方，就是它的工单，所以地图从不复述决策，只给一句摘要并放上链接。

**地图、它的子工单、阻塞关系、前沿查询具体存放在哪里，取决于所用的工单系统。** 工单系统本应已经提供给你。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。查阅该工单系统文档的 "Wayfinding operations"（寻路操作）一节，看_本_仓库怎么表达这些概念。如果没有提供任何工单系统，就默认用 local-markdown 工单系统。

### The map body（地图正文）

整张地图的低分辨率视图，每次会话加载一次。处于打开状态的工单**不**列出：它们是打开的子工单，靠查询找到。

```markdown
## Destination

<what reaching the end of this map looks like: the spec, decision, or change this effort is finding its way to. One or two lines; every session orients to it before choosing a ticket.>

## Notes

<domain; skills every session should consult; standing preferences for this effort>

## Decisions so far

<!-- the index: one line per closed ticket, enough to judge relevance, then zoom the link for the detail the ticket holds -->

- [<closed ticket title>](link): <one-line gist of the answer>

## Not yet specified

<!-- see "Fog of war": in-scope fog you can't ticket yet; graduates as the frontier advances -->

## Out of scope

<!-- see "Out of scope": work ruled beyond the destination; closed, never graduates -->
```

### Tickets（工单）

每张工单都是地图的**子工单**；工单系统里的 issue id 就是它的身份。它的正文就是那个问题，规模按一次 100K token 的智能体会话来定：

```markdown
## Question

<the decision or investigation this ticket resolves>
```

每张工单带一个 `wayfinder:<type>` 标签，取值是 `research`、`prototype`、`grilling`、`task` 之一（见 [工单类型](#ticket-types)）。`wayfinder:` 标签是地图及其工单唯一携带的标签，不会是 `ready-for-agent` 这类分诊标签：它们是决策，不是实现工作。

一次会话通过把工单指派给正在驱动地图的开发者来**认领**它，而且**先**做这一步，在任何工作之前，这样并发的会话就会跳过它。这个被指派人_就是_认领本身：一个打开且未被指派人的工单就是未被认领。

阻塞使用工单系统**原生**的依赖关系：这一点至关重要，因为它会在系统自己的界面里把前沿_可视化_呈现出来，人不打开地图就知道哪些可以接手。只有不具备原生阻塞能力的系统才退化到正文约定。当阻塞某张工单的所有工单都关闭了，这张工单就是**未阻塞**的；**前沿**是那些打开、未阻塞、未被认领的子工单，也就是已知之地的边缘。

答案不属于正文；它在解决时记录（见 [沿地图推进](#work-through-the-map)）。解决工单过程中创建的素材从工单里链接过去，不粘贴进去。

## Ticket Types（工单类型）

每张工单要么是 **HITL**（human in the loop，人在环内，由 agent _和_真人一起做，真人自己为自己发言），要么是 **AFK**（away from keyboard，人不在线），由 agent 单独推进。HITL 工单只能通过那场实时交流来解决；agent 绝不替人答他那半边（一个自问自答的 grilling agent 就已经破坏了这条）。

- **Research**（调研，AFK）：阅读文档、第三方 API，或者知识库这类本地资源，把一个决策正等着的事实挖出来。由一个 subagent 调用 Skill 工具、传入 "research" 来解决。当需要当前工作目录之外的知识时使用。
- **Prototype**（原型，HITL）：调用 Skill 工具、传入 "prototype"，做一个廉价、粗糙、具体的东西供人反应（一份大纲、一版粗略看法、一个桩，或者 UI/逻辑代码），以此提高讨论的保真度。把原型作为素材链接出来。当关键问题是"它该长什么样"或"它该有什么行为"时使用。
- **Grilling**（拷问，HITL）：对话。默认情况。始终调用 Skill 工具两次，分别传入 "grilling" 和 "domain-modeling"。
- **Task**（事务，HITL 或 AFK）：在能做出_决策_之前必须先完成的手工活：没有要拍板的、要做原型的、要调研的，但讨论被它挡住，做完才能继续。为了能评判某个服务的 API 而去注册它，去开通访问权限，为了能看清数据的形状而搬运数据。这是唯一一种_动手做_而不是_做决策_的类型，它凭的是给决策让路来立足，不是靠交付目的地。能自己推进的地方 agent 就单独推进（AFK）；否则交给真人一份精确的清单（HITL）。工作做完即算解决；答案里记下做了什么，以及后续工单依赖的由此产生的事实（凭证在哪、新的 URL、行数）。

## 战争迷雾

地图是_有意_画得不完整的：还看不见的东西就别去描绘。在活动工单之外是**战争迷雾**：那些你看得出会来、但还钉不住的决策和调查，影影绰绰，因为它们挂在仍未解决的问题上。解决一张工单会驱散它前面的雾，把此刻已经能够明确的部分升格成新工单，一次一张，直到通往目的地的路清楚、一张工单都不剩。

地图的 **Not yet specified**（尚未明确）一节就是写下这些模糊看法的地方：疑似的问题、之后要回来重看的领域。它是_朝向_目的地的未探明前沿：这里的一切都在范围内，只是还不够清晰，还不能成为工单。视图允许你写多松就写多松，允许写多全就写多全；它同时也是一块路标，给协作者指出这个项目正往哪去。

**是雾还是工单？** 判据是你此刻能不能把问题说准，_不是_你此刻能不能答上它。

- **该开工单**：问题已经很清晰，即使它被阻塞、你还不能对它采取行动。
- **该放进尚未明确**：你还不能把它表述得那么清晰。别把雾预先切成工单大小的碎块：它比工单粗，前沿推进到某一片之后，那一片可能升格成几张工单，也可能一张都不是。

**Not yet specified** 不包含已经定下的（Decisions so far）、已经成为活动工单的，以及超出范围的（下一节）。

## 超出范围

雾只在_朝向_目的地的方向上聚集。目的地钉定了范围，所以目的地之外的工作是**超出范围**：它不是雾，也不属于 **Not yet specified**。它在地图上有自己的 **Out of scope**（超出范围）一节：你有意从_本_项目里排除掉的工作。让它落到这一节的是范围，不是清晰度。

超出范围的工作永不升格（前沿止步于目的地），所以只有目的地被重新划定它才会回来，而且是以一个新项目的身份，不是接续。

把某件事划到范围外，是一个划定范围的动作，不是路线上的一步。当一张已经存在的工单被发现问题其实在目的地之外（绘制地图时圈错了范围，或者被某次解决暴露出来），**关掉它**（已关闭的工单明确不在前沿上），然后在 **Out of scope** 一节留一行：一句摘要加上它在范围外的理由，并链接那张已关闭的工单。它不进 **Decisions so far**，那一节记录的是真正走过的路线；范围边界不是路线上的一步。

## Invocation（调用方式）

两种模式。无论哪一种，**每次会话解决的工单绝不超过一张**，research 工单除外。

### Chart the map（绘制地图）

用户带着一个模糊的想法调用。

1. **给目的地命名。** 调用 Skill 工具两次，分别传入 "grilling" 和 "domain-modeling"，把这张地图要找路去往何处钉死：那份 spec、那个决策，或那处改动。目的地钉定范围，所以它最先定下来。
2. **摸清前沿。** 再拷问一轮，这次**广度优先**：在整个空间上铺开，而不是往某一条线里深挖，把仍未解决的决策和此刻就能迈出的头几步捞出来。**如果这一轮没浮出雾**（通往目的地的路本来就清楚，整段行程一个会话就装得下），那你不需要地图。停下来，问用户想怎么继续。
3. **创建地图**（标签 `wayfinder:map`）：Destination 和 Notes 填好，Decisions so far 留空，把雾的轮廓勾进 **Not yet specified**。
4. **创建此刻能够明确的工单**，作为地图的子工单，然后在**第二遍**里接上阻塞边（工单要先有 id 才能互相引用）。交叉引用也写在那第二遍里，用真实的 id：占位符 `#<n>` 会自动链到一个不相干的工单上。接线把它们归成前沿的和被阻塞的；凡是还不能明确的，都留在雾里：也就是 **Not yet specified** 一节。
5. **放出 research subagent。** 对你刚创建的每张 `research` 工单，起一个 subagent，调用 Skill 工具、传入 "research"，并行地解决它们，把它的发现记录在一条用后即弃的 `research/<name>` 分支上，并从工单留一个上下文指针过去。推送该分支，但不要开 pull request：它永远不会被合并。
6. 停止：绘制地图本身就是一次会话的工作量；它不替谁解决任何东西。

### Work through the map（沿地图推进）

用户带着一个地图调用（URL 或编号）。工单是**可选的**：没有指定工单，那就由你挑下一个决策，不由用户挑。

1. 加载**地图**：那份低分辨率视图，不是每张工单的正文。
2. 选工单。用户点名了某张，就用那张。否则按顺序取前沿上的第一张。**认领它**：在任何工作之前，先把它指派给自己。
3. 按它的 `wayfinder:<type>` 标签标明的类型来解决（见 [工单类型](#ticket-types)）。读标签，不只读正文：正文从不写明类型。**按需放大**：按需拉取任何相关或已关闭工单的完整正文；`## Notes` 一节点了哪些 Skill，就调用 Skill 工具去用它们。拿不准，就调用 Skill 工具两次，传入 "grilling" 和 "domain-modeling"。
4. 记录这次解决：把答案作为一条**解决评论**发出，**关闭**该工单，并在地图的 Decisions so far 末尾**追加一个上下文指针**。
5. 加入新浮现出来的工单（先创建、后接线）；把答案已经能够明确的雾升格为工单，并把每一处已升格的雾从 **Not yet specified** 里清掉，让它只以那张新工单的形式存在。如果答案显示某张工单（这张或别张）位于目的地之外，就**把它划到范围外**，而不是在路线上解决它。如果这个决策让地图的其他部分失效，就更新或删掉那些工单。

用户可能并行跑多张未被阻塞的工单，所以要预期有其他会话在同时编辑工单系统。
