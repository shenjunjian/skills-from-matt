# Wizard（向导）

**wizard** 是一个 bash 脚本，带真人一步一步走完一套手工流程：手动做很繁琐，每次都重新向 AI 解释同样繁琐。它打开每个 URL，说清该点什么、该复制什么，把值收集起来，写到它们该去的地方（`.env`、GitHub secrets），每个阶段都确认一次，并告诉你还剩几个阶段。它可能用来配置第三方服务、跑一次迁移，或把项目从一个状态挪到另一个状态。

讨人喜欢的体验已经被 [template.sh](template.sh) 解决了：按阶段推进的进度、确认闸门、跨平台的 URL 打开（包括 WSL）、隐藏输入的 secret、幂等的 `.env` upsert、`gh secret`/`gh variable` 写入，以及结尾的总结。**你的活儿只是界定这套流程的范围并写出它的各个阶段。** `STAGES` 标记之上那部分库代码在每个 wizard 里都一模一样；这份一致就是重点：绝不要手改它。

wizard 默认是一次性的：为一次运行而生，存到临时路径或 `scripts/` 路径，事情办完就删。只有当用户想要一条可重复的配置路径、希望它留在仓库里时，才提交它。

## Process（流程）

### 1. 界定流程范围

理清真人必须走的每一步，以及一路上要收集的每一个值。先读仓库，别开口就问：

- 配置类：`.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置，以及 `.github/workflows/*`（每一处 `secrets.*` / `vars.*` 引用，都是 wizard 必须产出的一个值）。
- 迁移或切换类：当前状态、目标状态，以及两者之间那些不可逆的动作。

然后给用户看排好序的阶段列表，以及每个阶段产出哪些值，并请他确认：他可以增、删、调整顺序。

**完成标准：** 每个阶段都按顺序点了名，并且对每个要收集的值，你知道 (a) 真人从哪里拿到它，(b) 它写到哪里（`.env`、一个 GitHub secret、两者都要，或者哪儿都不写；有些阶段是纯动作），(c) 它是 secret（隐藏输入）还是公开值。

### 2. 排出每个阶段的操作路线

给每个阶段写下真人要走的确切路径：打开哪个 URL、在那里做什么、值在哪儿显示、它填的是哪个变量；比如 "Dashboard → Developers → API keys → Reveal test key → copy"。你真的不清楚当前界面或确切命令的地方，直说，然后问用户或查文档：绝不凭空编出可能不存在的步骤。

**完成标准：** 每个阶段都能落到陌生人照着走的具体指令上。

### 3. 写出 wizard

把 `template.sh` 复制到目标路径。用每个步骤对应一个 `stage` 的方式替换掉那个示例阶段，按依赖顺序排列。用库里的辅助函数：`stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm`。把 `TOTAL_STAGES` 设成你写的阶段数。

守住模板立下的标准：先打开 URL，再问它对应的值；凡是 secret 一律用 `ask_secret`；每个要持久化的值都用 `write_env` 写入；`set_secret` 只写 CI 真正需要的值；任何不可逆动作之前先 `confirm`。每个 `stage` 都会清屏，只留下当前这一步可见：所以一个阶段只做一件集中的事，别让真人需要的内容被滚走。别碰标记之上的库代码。

### 4. 校验并交接

- `bash -n <script>`；有 `shellcheck` 就跑一遍。
- `chmod +x <script>`。
- 别自己从头到尾跑一遍：它会打开浏览器并卡在真人输入上。改为静态通读：第 1 步里的每个值都被收集到了，并且落在第 1 步说的那个位置；每个 `set_secret` 的名字和 CI 里的 `secrets.*` 引用完全对得上。
- 告诉用户怎么运行它。如果这是一条可重复的配置路径，就提交它，并从 README 链接过去，让下一个人跑脚本，而不是去问 AI。
