# 诊断缺陷

一套应对疑难缺陷的纪律。只有在明确说得通的情况下才跳过某个阶段。

探索代码库时，先读 `GLOSSARY.md`（如果存在），对相关 module 建立清晰的心智模型；并查一下你要改动的那块区域里的 ADR。

## 脱敏

这个 skill 会让你展示命令、输出和抓取到的产物。**先给每一处密钥脱敏**：在原位置写 `<REDACTED>`。构建循环时读取环境变量，让凭据留在环境里，而不是出现在你展示的内容中。抓取到的产物带着认证头：只引用真正携带信号的那几行。

如果脱敏后的输出不足以诊断缺陷，直说，并向用户索取。

## 阶段 1：建立一个反馈循环

**这个 skill 讲的就是这件事。** 其余都是机械劳动。只要你对这个缺陷有一个**紧凑的**通过/失败信号（一个会在_这个_缺陷上变红的信号），你就一定能找到原因；二分、假设验证、埋点，全都只是消费它。如果你没有这样的信号，再怎么盯着代码看也救不了你。

在这里投入不成比例的时间。**要激进。要有创造力。别轻易放弃。**

### 构造它的几种办法，大致按这个顺序

1. **失败的测试**，落在任何能触达缺陷的 seam 上：单元、集成、e2e。
2. 对着运行中的开发服务器发起 **curl / HTTP 脚本**。
3. **CLI 调用**，喂一个 fixture 输入，把 stdout 与一份已知正确的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer），驱动 UI 并对 DOM/console/网络做断言。
5. **重放抓取到的 trace。** 把一个真实的网络请求 / 载荷 / 事件日志存到磁盘，让它在隔离环境中重放走一遍缺陷代码路径。
6. **一次性 harness。** 起一个系统的最小切片（一个服务，依赖全部 mock），用一次函数调用把缺陷代码路径跑起来。
7. **属性 / fuzz 循环。** 如果缺陷表现为"输出偶尔不对"，就跑 1000 个随机输入，找那个失败模式。
8. **二分 harness。** 如果缺陷出现在两个已知状态之间（commit、数据集、版本），就把"在状态 X 启动、检查、重复"自动化，这样你可以用 `git bisect run`。
9. **差分循环。** 把同一个输入分别跑旧版本与新版本（或两个配置），再对输出做 diff。
10. **HITL bash 脚本。** 最后的办法。如果必须有人来点击，就用 `scripts/hitl-loop.template.sh` 来指挥_那个人_，让循环仍然是有结构的。抓取到的输出会回传给你。

把正确的反馈循环搭起来，缺陷就修好了 90%。

### 收紧循环

把循环本身当成一个产品。一旦你有了_一个_循环，就去**收紧**它：

- 我能让它更快吗？（缓存准备工作、跳过无关的初始化、缩小测试范围。）
- 我能让信号更锐利吗？（针对具体症状做断言，而不是"没崩"。）
- 我能让它更确定吗？（固定时间、给定 RNG 播种、隔离文件系统、冻结网络。）

一个 30 秒且时好时坏的循环，比没有循环好不了多少；一个 2 秒且确定的循环才是紧凑，那是调试的超能力。

### 非确定性缺陷

目标不是一次干净的复现，而是**更高的复现率**。把触发路径循环 100 次、并行化、加压、收窄时间窗口、插入 sleep。50% 概率失败的缺陷可以调试，1% 不行，所以要不断抬高复现率，直到它可调试。

### 当你确实建不出循环

停下来，明确说明。列出你试过的办法。向用户索取：(a) 能够复现它的那个环境的访问权限，(b) 一份脱敏后的抓取产物（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 临时在生产环境加埋点的许可。**不要**在没有循环的情况下就去提假设。

### 完成标准：一个会变红的紧凑循环

阶段 1 完成的标志是循环**紧凑**且**可变红**：你能说出**一条命令**（脚本路径、测试调用、一次 curl），你**至少已经运行过一次**（展示那次调用及其输出，脱敏后），并且它满足：

- [ ] **可变红**：它驱动真实的缺陷代码路径，并对**用户描述的那个确切症状**做断言，因此它能在这个缺陷上变红、修好后变绿。不是"跑起来不报错"；它必须能够_逮住这个具体的缺陷_。
- [ ] **确定**：每次运行给出同样的结论（时好时坏的缺陷：按上文所述，锁定一个高复现率）。
- [ ] **快**：以秒计，不是以分钟计。
- [ ] **可由 agent 运行**：你能无人值守地跑它；人在环路中只通过 `scripts/hitl-loop.template.sh` 参与。

如果你发现自己在命令还不存在时就去读代码以构建理论，**停下：直接跳到假设，正是这个 skill 要防止的那个错误**。没有可变红的命令，就没有阶段 2。

## 阶段 2：复现 + 最小化

运行循环。看着它在缺陷出现时变红。

确认：

- [ ] 循环产出的是**用户**描述的那个失败模式，而不是旁边恰好发生的另一个失败。缺陷认错，修复就会认错。
- [ ] 这个失败在多次运行中都能复现（对非确定性缺陷，复现率高到足以支撑调试）。
- [ ] 你已经记下那个确切症状（错误消息、错误的输出、缓慢的耗时），后续阶段才能验证修复确实针对它。

### 最小化

一旦变红，就把复现缩到**仍能变红的最小场景**。逐个削减输入、调用方、配置、数据和步骤，每削一次就重跑一遍循环，只留下对失败真正起作用的那部分。

为什么要费这一步：最小的复现会缩小阶段 3 的假设空间（剩下可疑的活动部件更少），并且它会成为阶段 5 里那个干净的回归测试。

完成的标志是**剩下的每个元素都在承重**：去掉其中任何一个，循环就变绿。

在你既复现**又**最小化之前，不要往下走。

## 阶段 3：提出假设

在验证任何一个之前，先生成 **3 到 5 个排好序的假设**。只生成一个假设的思路会锚定在第一个看上去合理的想法上。

每个假设都必须**可证伪**：说出它做出的预测。

> 格式："如果 <X> 是原因，那么<改动 Y>会让缺陷消失 / <改动 Z>会让它更严重。"

如果你说不出预测，这个假设就是一种感觉：扔掉它，或者把它磨尖。

**在验证之前把这份排序清单展示给用户。** 他们往往具备领域知识，能立刻重排（"我们刚部署了一次改动，动的是 #3"），或者知道哪些假设他们已经排除过。开销很小的一个检查点，却省下大量时间。不必为此等待；如果用户不在，就按你自己的排序继续。

## 阶段 4：埋点

每一个探针都必须对应阶段 3 里的某一条具体预测。**一次只改一个变量。**

工具偏好顺序：

1. 环境支持的话就用**调试器 / REPL 检视**。一个断点胜过十条日志。
2. 在能区分各个假设的边界处打**精准的日志**。
3. 绝不要"把所有东西都打出来再去 grep"。

**给每条调试日志都打上标签**，用一个唯一的前缀，例如 `[DEBUG-a4f2]`。最后的清理就成了一次 grep。没标签的日志会活下来，有标签的会被清掉。

**性能分支。** 性能回退通常不该用日志。改成：先确立一个基线测量（计时 harness、`performance.now()`、profiler、query plan），然后二分。先测量，再修复。

## 阶段 5：修复 + 回归测试

在修复**之前**先写回归测试，但前提是存在一个**正确的 seam**。

正确的 seam 是指：测试在这个 seam 上驱动的，是调用点上真实出现的**那个缺陷模式**。如果唯一可用的 seam 太浅（缺陷需要多个调用方，测试却只有一个调用方；单元测试无法重现触发缺陷的那条调用链），那么在这个位置放回归测试只会带来虚假的信心。

**如果没有正确的 seam，这件事本身就是发现。** 记下来。是代码库的架构在阻止这个缺陷被锁死。把这一点标记给下一个阶段。

如果存在正确的 seam：

1. 把最小化的复现变成该 seam 上一个失败的测试。
2. 看着它失败。如果你是靠改动代码或改动 fixture 强行制造的红色，那就对着一份原始副本做 `diff`，证明那处改动确实生效了，然后再信它。
3. 应用修复。
4. 看着它通过。
5. 针对原始（未最小化）的场景，重跑一遍阶段 1 的反馈循环。

## 阶段 6：清理

宣布完成之前必须做到：

- [ ] 原始复现场景不再能复现（重跑阶段 1 的循环）
- [ ] 回归测试通过（或者 seam 的缺失已被记录）
- [ ] 所有 `[DEBUG-...]` 埋点都已移除（对前缀做 `grep`）
- [ ] 一次性原型已删除（或移入一个明确标注的调试位置）
- [ ] 最终被证明正确的那个假设已写进 commit / PR 说明，让下一个调试的人能学到
