# ADR 格式

ADR 放在 `docs/adr/` 下，按顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。

`docs/adr/` 目录按需创建：只在需要第一份 ADR 时才建。

## 模板

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

就这样。一份 ADR 可以只有一段。价值在于记录下*做出过*某个决定以及*为什么*，而不在于把各个小节填满。

## 可选小节

只在确实能带来价值时才加上这些小节。多数 ADR 都不需要。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决定被重新审视时有用
- **Considered Options（考量过的选项）**：只有当被否决的方案值得记住时
- **Consequences（后果）**：只有当需要点出不明显的下游影响时

## 编号

扫描 `docs/adr/`，找到现存的最大编号，加一。

## 什么时候该给出 ADR

以下三条必须同时成立：

1. **难以回退**：日后反悔的代价不小
2. **脱离上下文会让人意外**：后来的人读代码会想"到底为什么会这么做？"
3. **是真实取舍的结果**：确实存在别的方案，你出于具体理由选了一个

如果一个决定容易回退，就别写：你迟早会回退它。如果不让人意外，没人会追问为什么。如果没有真正的备选方案，那除了"我们做了显然该做的事"之外也没什么可记录的。

### 哪些情况算数

- **架构形态。**"我们用 monorepo。""写模型采用事件溯源，读模型投影到 Postgres。"
- **上下文之间的集成方式。**"Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。"
- **带来锁定的技术选择。**数据库、消息总线、认证服务商、部署目标。不是每个库都写：只写那些换掉要花掉一个季度的。
- **边界与范围的决定。**"客户数据归 Customer 上下文所有，其他上下文只按 ID 引用它。"明确说不的与明确说是的同样有价值。
- **有意偏离显然的做法。**"因为 X，我们用手写 SQL 而不是 ORM。"凡是讲道理的读者都会猜反了的，都算。这些记录能阻止下一位工程师去"修好"一个本来刻意为之的地方。
- **代码里看不出的约束。**"因为合规要求，我们不能用 AWS。""按合作方 API 约定，响应时间必须低于 200ms。"
- **否决理由不明显的备选方案。**如果你考虑过 GraphQL，出于细微的原因选了 REST，就记下来；否则半年后又会有人提议 GraphQL。
