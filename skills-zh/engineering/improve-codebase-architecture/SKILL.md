# 改进代码库架构

把架构上的摩擦暴露出来，并提出**加深机会**：把浅模块改造成深模块的重构。目标是可测试性与可被 AI 导航性。

这条命令的判断**依据**项目的领域模型，并建立在一套共享的设计词汇之上：

- 调用 Skill 工具，用 "codebase-design" 取得架构词汇（**module**、**interface**、**depth**、**seam**、**adapter**、**leverage**、**locality**）及其原则（删除测试，"interface 就是测试面"，"一个 adapter = 假设的 seam，两个才是真的"）。每条建议里都要精确使用这些词，不要漂到"组件""服务""API""边界"上去。
- `GLOSSARY.md` 里的领域语言为好 seam 提供名字；`docs/adr/` 里的 ADR 记录了这条命令不该重开的话题。

## 流程

### 1. 探索

**扫描之前先划定范围：YAGNI。**加深一个模块，回报来自让它日后的改动更容易，所以把更多权重放在代码库最近变动过的部分。看哪里，要在动手看之前定下来：

- 用户点明了方向（某个模块、某个子系统、某个痛点），就照着走，跳过下面的推断。
- 否则，往回走一段足够长的提交历史（`git log --oneline`），找出代码库的热点、那些反复出现的文件和区域，让注意力先被这些路径吸过去。如果改动很分散、没有明显热点，就把网撒宽。

先读项目的领域术语表（`GLOSSARY.md`），以及你正在触及的那片区域的 ADR。

然后派一个 subagent 走查代码库。不要死守刻板的启发式规则；有机地探索，并记下你感到摩擦的地方：

- 理解一个概念，要在许多小模块之间来回跳转的地方在哪里？
- **浅**的 module 在哪里，interface 的复杂度几乎赶上 implementation？
- 只为了可测试而抽出纯函数，真正的缺陷却藏在调用方式里的地方（缺 **locality**）在哪里？
- 紧耦合的 module 从它们的 seam 泄漏出去的地方在哪里？
- 哪些部分没有测试，或者难以通过它当前的 interface 来测试？

对你怀疑是浅的任何东西套用**删除测试**：删掉它，是让复杂度聚集起来，还是仅仅把它挪个位置？"是，会聚集"就是你要的信号。

### 2. 以 HTML 报告呈现候选项

写一个自包含的 HTML 文件到操作系统临时目录，这样任何东西都不会落到仓库里。临时目录从 `$TMPDIR` 解析，取不到就退回 `/tmp`（Windows 上是 `%TEMP%`），写到 `<tmpdir>/architecture-review-<timestamp>.html`，让每次运行都得到一个全新文件。为用户打开它（Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`），并告诉他绝对路径。

报告的布局和样式用 **Tailwind（CDN 引入）**，在图/流/时序能可靠表达结构的地方用 **Mermaid（CDN 引入）**画示意图。Mermaid 与手工写的 CSS/SVG 视觉混用：关系是图状的（调用图、依赖、时序）就用 Mermaid，想要更有编辑感的（质量图、剖面图、收拢动画）就用手写 div/SVG。每个候选项都要有**前后对比的可视化**。多给视觉，少给空话。

每个候选项渲染一张卡片，包含：

- **文件**：涉及哪些文件/模块
- **问题**：当前架构为什么造成摩擦
- **方案**：用平实的话说明会怎么改
- **收益**：从 locality 和 leverage 来讲，并说明测试会怎么改善
- **Before / After 示意图**：并排手绘，把浅和加深都画出来
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 三者之一，渲染成徽章

报告结尾放一个**首选推荐**小节：你会先动哪个候选项，以及为什么。

**领域用 GLOSSARY.md 的词汇，架构用 `/codebase-design` 的词汇。**如果 `GLOSSARY.md` 定义了 "Order"，就说"Order intake module"，别说"FooBarHandler"，也别说"Order service"。

**与 ADR 冲突**：某个候选项与现存 ADR 相抵触时，只在摩擦确实大到值得重开那份 ADR 时才把它摆出来。在卡片里明确标注（例如一个警告提示框：_"与 ADR-0007 相抵触，但值得重开，因为……"_）。不要把 ADR 否决掉的每一个理论上的重构都列一遍。

完整的 HTML 骨架、示意图式样和风格指引见 [HTML-REPORT.md](HTML-REPORT.md)。

先不要提出任何 interface。文件写好之后，问用户："这几个里你想深入看哪一个？"

### 3. 追问循环

用户选定一个候选项后，调用 Skill 工具，用 "grilling" 陪他走这棵决策树：约束、依赖、加深之后的 module 长什么样、seam 后面放什么、哪些测试还能活下来。

决定成形的同时就地处理副作用；调用 Skill 工具，用 "domain-modeling" 让领域模型保持在最新：

- **要用一个不在 `GLOSSARY.md` 里的概念给加深后的 module 命名？**把这个术语加进 `GLOSSARY.md`。文件不存在就按需创建。
- **对话中把一个含混的术语磨清楚了？**当场更新 `GLOSSARY.md`。
- **用户用一个吃重的理由否决了这个候选项？**提议写一份 ADR，措辞是：_"要不要我把这记录成 ADR，好让以后的架构评审不再重复建议它？"_ 只有当这个理由确实是后来的探索者避免重复建议所需的信息时才提议；跳过一时的理由（"现在不值得"）和不言自明的理由。
- **想为加深后的 module 探索别的 interface？**调用 Skill 工具，用 "codebase-design"，取它的设计两遍（design-it-twice）并行 subagent 模式。
