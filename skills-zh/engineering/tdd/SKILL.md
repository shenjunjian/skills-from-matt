# 测试驱动开发

TDD 是 red → green 循环。这个 skill 是一份参考文档，让这个循环产出值得保留的测试：好测试是什么样的、测试放在哪里、有哪些反模式，以及循环的规则。每一节在每个循环里都适用：在循环之前和循环进行中查阅它们，而不是事后。

浏览代码库时，读 `GLOSSARY.md`（如果它存在），让测试名称和接口用词与项目的领域语言一致，并遵守你所在改动区域的 ADR。

## 好测试是什么样的

测试通过公开接口验证行为，而不是实现细节。代码可以整体改掉，测试不应该。好测试读起来像一份规格说明："user can checkout with valid cart" 准确地告诉你系统存在什么能力，而且它不关心内部结构，所以能在重构中存活。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

## Seam：测试放在哪里

**seam** 是你进行测试的公开边界：在这个接口上观察行为，不用伸进内部。测试位于 seam 上，绝不针对内部实现。

**只在事先商定的 seam 上测试。** 写任何测试之前，先记下要测的 seam 并与用户确认。未确认的 seam 上不写测试。你不可能测尽一切，所以提前商定 seam，测试精力才会落在关键路径和复杂逻辑上，而不是每个边角情况。

要问："公开接口是什么，我们应该测哪些 seam？" 给每个提出的 seam 写一行说明，讲清它能抓到什么、会漏掉什么。

当这个接口本身的形态存疑（模块有多深、seam 该设在哪里、接口应该暴露什么），调用 Skill 工具并传入 "codebase-design" 来获取用词。它是 module、interface、depth、seam、adapter、leverage、locality 这些术语的共同出处，是一份要查阅的参考，不是一个要运行的会话。

## 反模式

- **实现耦合**：mock 内部协作者、测试私有方法，或通过旁路验证（查询数据库而不是走接口）。识别特征：行为没变，但你一重构测试就挂。
- **同义反复**：断言用和代码相同的方式重新算出期望值（`expect(add(a, b)).toBe(a + b)`、同样手工推导出来的快照、断言一个常量等于自身），于是它按构造必然通过，永远不可能和代码不一致。期望值必须来自独立的权威来源：一个已知正确的字面量、一个算好的示例、一份 spec。
- **横向切分**：先写完所有测试，再写所有实现。成批写出的测试验证的是 _想象的_ 行为：你测的是事物的 _形状_ 而不是面向用户的行为，测试对真实改动变得迟钝，而你在理解实现之前就把测试结构定了下来。改为 **vertical slice**：一个测试 → 一个实现 → 重复，每个测试都是一颗 **tracer bullet**，回应上一个循环教会你的东西。

## 循环的规则

- **先 red，后 green。** 先写失败的测试，再写刚好够通过的代码。不要预想后面的测试，也不要加投机性的功能。
- **一次一个 slice。** 每个循环一个 seam、一个测试、一个最小实现。
- **重构不在这个循环里。** 它属于评审阶段（见 `code-review` skill），不属于 red → green 的实现循环。
